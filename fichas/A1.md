# Ficha A1 — BOLA en pedidos (acceso a pedidos ajenos)

> App vulnerable a propósito — solo laboratorio (127.0.0.1). Datos 100 % ficticios.
> Categoría OWASP: **API1:2023 Broken Object Level Authorization**. Flag: `VULN_A1=on|off`.
> Módulo: `api/src/vulns/a1.ts`.

## Qué es
El detalle de un pedido se consulta en `GET /api/v2/orders/:id`. La ruta exige estar
autenticado, así que un desconocido no entra. Pero autenticación no es autorización: estar
dentro de la tienda no da derecho a ver **cualquier** pedido. Con `VULN_A1=on`, cualquier
cliente con sesión puede pedir el `id` de otro y recibir su pedido completo (monto, cupón,
reliquias compradas). Es la fuga de datos entre clientes más común en APIs.

## Por qué ocurre: autorización por función vs. por objeto
- **Por función** (la que sí hay): «¿puede este rol usar este endpoint?». La resuelve
  `requireAuth`: hay sesión válida → pasa. Necesaria, pero insuficiente.
- **Por objeto** (la que falta en `on`): «¿este objeto concreto pertenece a quien lo pide?».
  Esa comprobación es el **predicado de propiedad** y debe vivir en la consulta misma.

La consulta vulnerable (resumida) filtra solo por el id del recurso:

```
... FROM orders WHERE id = ?        -- falta: AND customer_id = <sesión>
```

El `id` lo elige el atacante. Como no se cruza con el dueño de la sesión, pedir el id de otro
devuelve su pedido. La causa raíz no es el id adivinable (usar UUID solo lo esconde): es
**no verificar la propiedad del objeto**.

## La línea corregida (`VULN_A1=off`)
El predicado de propiedad vuelve a la consulta: se filtra por `id` **y** `customer_id` de la
sesión. Un pedido ajeno simplemente no aparece y la ruta responde **404** (no `403`): así no
se confirma siquiera que ese id exista, y no se filtra información por el código de estado.

```
... FROM orders WHERE id = ? AND customer_id = ?   -- no coincide → 404
```

## Cómo practicarlo (herramienta de práctica)
Con la API del lab corriendo en local y `VULN_A1=on`:

1. Inicia sesión como Benjamín (cliente B) y guarda su token.
2. Control legítimo: `GET /api/v2/orders/2` con el token de B → 200, su propio pedido.
3. Acceso ajeno: `GET /api/v2/orders/1` con el token de B → en `on` responde 200 con el pedido
   de Camila (cliente A, `customer_id` 2). Esa es la fuga.
4. En **Burp Suite**: captura el paso 2 y manda el request a *Repeater*; cambia el `id` de 2 a 1
   y reenvía. Con *Intruder* y una lista de ids se enumera a quién pertenece cada pedido.
5. Enciende la corrección (`VULN_A1=off`) y repite el paso 3: ahora responde 404. Esa es la
   calibración del arnés (`exploits/test_a1.py`): explotado en `on`, bloqueado en `off`.
