# Ficha A5 — SSRF al publicar reliquia con imagen por URL

> App vulnerable a propósito — solo laboratorio (127.0.0.1). Datos 100 % ficticios.
> Categoría OWASP: **API7:2023 SSRF** · **A01:2025**. Flag: `VULN_A5=on|off`.
> Módulo: `api/src/vulns/a5.ts`.

## Qué es
Al publicar una reliquia, el admin puede dar la imagen como una **URL** (`image_url`): el
servidor la **trae** (`fetch`) para validarla y guardarla. Con `VULN_A5=on` el servidor hace
esa petición **sin validar el destino**. Un admin —o quien tome su sesión por otra vuln— apunta
`image_url` a una dirección interna (`http://127.0.0.1:<puerto>/...`) y el servidor la consulta
**por él**. Eso es SSRF: *Server-Side Request Forgery*. El atacante no alcanza la red interna;
el servidor sí, y lo convierte en su proxy hacia servicios que solo escuchan en loopback
(bases de datos, paneles, metadatos de la nube).

## Por qué ocurre: confianza en una URL que elige el cliente
La trampa es tratar `image_url` como un dato inocente. El servidor tiene una posición de red
privilegiada (ve `localhost`, la subred privada, el link-local), y al traer una URL arbitraria
le **presta** esa posición a quien la escribió.

- **Validar el esquema no basta.** Exigir `http(s)` evita `file://` o `gopher://`, pero
  `http://127.0.0.1:6379/` sigue siendo interno.
- **El destino es lo que importa.** Hay que resolver el host y **negar** todo lo que caiga en
  rangos internos: loopback (`127.0.0.0/8`, `::1`), privados (`10/8`, `172.16/12`,
  `192.168/16`) y link-local (`169.254/16`, incluida la IP de metadatos de la nube).

```
// on (defecto): fetch sin mirar a dónde
await fetch(image_url)   // image_url = http://127.0.0.1:6379/  → el servidor lo consulta
```

## La corrección (`VULN_A5=off`)
Antes de traer nada se valida la URL: solo `http(s)` y se **rechaza** todo host que resuelva a
loopback/privado/link-local (incluido `0.0.0.0` y `::`) → `400 BAD_REQUEST`. Además el `fetch`
usa `redirect:'manual'`, así que una respuesta 3xx (un redirector externo que apunta a interno)
no se sigue: rebota con 400. Con eso, los vectores de **URL directa** y de **redirección** a un
destino interno quedan cerrados antes de alcanzar nada.

```
// off: se valida el destino; lo interno rebota antes del fetch
http://127.0.0.1:<puerto>/...  → 400, no se hace la petición
```

**Qué NO cubre (y por qué «nunca» sería mentira).** Esta corrección valida el destino, no cada
vector. Queda fuera a propósito el **DNS rebinding** (un host que resuelve a una IP pública en la
validación y a una interna en el `fetch`): cerrarlo exige fijar la IP resuelta y reusarla en la
conexión, un paso aparte. En producción el siguiente escalón es una **allowlist** de dominios.
Nota: aun en `on`, el servidor solo publica si los bytes traídos son una imagen válida
(`detectarTipo`), así que lo explotable es **SSRF ciego** —sondeo de puertos y servicios por
código/tiempo de respuesta—, no la lectura del cuerpo de la respuesta interna.

## Cómo practicarlo (herramienta de práctica)
Con la API del lab corriendo en local y `VULN_A5=on`:

1. Levanta un servicio de mentira en loopback (p. ej. `python -m http.server 9000`) que anote
   cada visita.
2. Inicia sesión como admin del seed (`admin@trastomaldito.test`) y guarda el token.
3. `POST /api/v2/admin/relics` con los campos obligatorios y
   `image_url: "http://127.0.0.1:9000/interno"`.
4. En `on`, tu servicio de mentira **registra la visita**: el servidor hizo la SSRF por ti. En
   **Burp Suite** se captura el POST en *Repeater* y se varía `image_url` para sondear puertos
   internos (la diferencia de tiempo o de código delata qué responde).
5. Enciende la corrección (`VULN_A5=off`) y repite: responde **400** y tu servicio **no**
   recibe nada. Esa es la calibración del arnés (`exploits/test_a5.py`): el loopback fue
   contactado en `on`, no en `off`.
