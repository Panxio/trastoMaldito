# Ficha W3 — Errores verbosos de la API (fuga del detalle interno)

> App vulnerable a propósito — solo laboratorio (127.0.0.1). Datos 100 % ficticios.
> Categoría OWASP: **A02:2025 Security Misconfiguration**. Flag: `VULN_W3=on|off`.
> Módulo: `api/src/vulns/w3.ts`.

## Qué es
Toda API falla: un cuerpo mal formado, un tipo equivocado, una excepción no prevista. Lo que
el servidor **responde** ante ese fallo es una decisión de diseño. Con `VULN_W3=on`, ante un
error inesperado la API devuelve al cliente el detalle interno: el mensaje crudo del framework
(`detail`) y la **traza de la pila** (`stack`), con rutas de archivos del servidor, versiones
de librerías y la estructura del proyecto. Un atacante no necesita entrar: provoca un error y
lee las tripas del backend, que luego usa para afinar su ataque.

## Por qué ocurre: el handler serializa el objeto de error
El manejador de errores distingue dos clases:
- **Error esperado** (`ApiError`): ya trae un código y un mensaje pensados para el público
  (`404 NOT_FOUND`, `401 INVALID_CREDENTIALS`). Sale tal cual; nunca fue el problema.
- **Error inesperado**: una validación de esquema (4xx) o una excepción (500). Aquí está la
  tentación: serializar el objeto `Error` «para depurar». Eso es lo que `on` hace.

```
// on (defecto): el cuerpo añade el detalle interno
{ code, message, detail: err.message, stack: err.stack }
```

El `stack` de un error de validación es el mismo tipo de traza que saldría en un 500: revela
`node_modules/fastify/...`, la ruta absoluta del proyecto, nombres de funciones internas. La
causa raíz no es «qué error ocurrió», sino que **el handler nunca debe mandar el objeto de
error al cliente**.

## La corrección (`VULN_W3=off`)
El cuerpo inesperado es genérico y estable: solo `{code, message}` fijos. El detalle interno
(traza, mensaje del framework) **nunca sale al cliente**: su único lugar legítimo es el **log del
servidor**, donde el operador lo ve y el atacante no.

```
// off: cuerpo estable; el detalle no viaja al cliente
{ code: 'BAD_REQUEST', message: 'Solicitud inválida' }
```

> Nota honesta del lab: hoy la API corre con el logger de peticiones apagado (`logger:false` en
> `server.ts`), así que `req.log.error(err)` no escribe en ninguna parte y la traza se descarta.
> Para la respuesta al cliente da igual —el atacante no la recibe en ningún caso—, pero que no
> quede **ningún** rastro para el operador es, en sí, un fallo de registro y alerta. El lab lo
> trata como vulnerabilidad propia: **A09:2025 (Security Logging & Alerting Failures)**, la
> unidad siguiente.

## Cómo practicarlo (herramienta de práctica)
Con la API del lab corriendo en local y `VULN_W3=on`:

1. Provoca un error de validación: `POST /api/v2/auth/login` con un cuerpo al que le falta
   `password` (p. ej. `{"email":"quien@sea.test"}`). Responde **400**.
2. Mira el cuerpo: en `on` trae un campo `stack` con la traza del servidor (rutas, versiones).
   Esa es la fuga. En **Burp Suite**, cualquier request malformado al *Repeater* la revela.
3. Enciende la corrección (`VULN_W3=off`) y repite: el `400` ya no trae `stack` ni `detail`,
   solo `{code, message}`. Esa es la calibración del arnés (`exploits/test_w3.py`): explotado
   en `on` (hay `stack`), bloqueado en `off` (no lo hay).
